## 2. ТЕХНИЧЕСКОЕ ПРОТИВОРЕЧИЕ — RVC ЛИЦЕНЗИЯ (AGPL-3.0)

**Dev2:** Вот это критический момент. Если мы используем RVC как есть, плагин должен быть распространён под AGPL-3.0. Это означает, что любой, кто модифицирует нашу кодовую базу, должен опубликовать исходный код.

**PM:** Погоди, а это проблема для коммерческого продукта?

**Dev1:** Огромная проблема. AGPL не просто copyleft, как GPL. AGPL требует открыть исходный код даже при сетевом использовании. Если мы хотим лицензировать плагин коммерчески, это противоречит AGPL.

**PM:** То есть мы не можем продавать плагин под AGPL?

**Dev2:** Технически можем, но тогда наши клиенты получают право модифицировать исходный код и распространять свои версии. Это убивает коммерческую модель.

**Designer:** А есть альтернативы RVC?

**Dev2:** Да, несколько:
1. **so-vits-svc** — MIT лицензия, но менее функциональная
2. **Собственная модель** — обучаем на нашем наборе данных, полная контроль над лицензией
3. **Лицензионное соглашение с RVC авторами** — платим им за коммерческое использование

**Dev1:** Я бы против so-vits-svc. Quality будет ниже. Собственная модель — это долгая история, нужен большой датасет.

**PM:** А коммерческое соглашение с RVC авторами?

**Dev2:** Это один из немецких разработчиков. Нужно разбираться. Но лучший путь, на мой взгляд — это модифицировать RVC, убрать AGPL-зависимости и переписать под MIT или Apache 2.0.

**Dev1:** Сложно это будет?

**Dev2:** Нужно переписать inference часть, проверить, что результаты совпадают. Я бы сказал 2-3 недели на это.

**PM:** Окей, решение такое: Dev2, берёшь на себя переписывание RVC inference части под лицензию Apache 2.0. Это критиче для коммерчески модели. Это входит в MVP timeline или добавляет время?

**Dev2:** Это добавляет время, но не критично. Можно параллельно с интеграцией делать. Я бы сказал +2 недели к общему timeline.

**PM:** Принято. RVC переписываем под Apache 2.0, плагин распространяем под той же лицензией.

## 3. LATENCY БЮДЖЕТ — РЕАЛЬНЫЕ ЦИФРЫ

**Dev1:** Теперь про latency. Это очень важная тема. Real-time pitch correction в аудиоплагине — это жёсткие ограничения по скорости.

**Dev2:** Я провёл бенчмарки RVC:
- **CPU inference (ONNX Runtime):** 200-500ms
- **GPU inference (CUDA):** 20-50ms
- **Batch processing:** можно оптимизировать до 10-20ms на GPU

Для сравнения: буфер в DAW обычно 256 сэмпла при 44.1kHz это ~5.8ms.

**PM:** То есть RVC real-time невозможна?

**Dev1:** Правильно. 200-500ms это слышимая задержка. Для real-time нужно <10ms максимум.

**Designer:** Это означает, что пользователь не может слышать результат в реальном времени во время пения?

**Dev2:** Точно. Нужно делать offline режим:
1. Пользователь записывает свой голос
2. Плагин обрабатывает offline (может быть несколько секунд)
3. Выдаёт результат

**Dev1:** А для real-time feedback мы используем DSP pitch correction. Это быстро, но менее красиво. Это даёт пользователю примерное представление о том, что получится.

**PM:** Какой DSP есть для pitch correction?

**Dev1:** JUCE имеет основы, но мы можем интегрировать Elastique Pitch от zplane (платный) или использовать PhaseVocoder. Я бы рекомендовал собственный DSP, основанный на Phase Vocoder + небольшой ML модельки для detune.

**Dev2:** Есть свободные модели для этого? TortoiseVC, Piper...

**Dev1:** Да, но для real-time нужна очень лёгкая модель. Можем обучить собственный NN, который весит <50MB и работает <5ms.

**PM:** Окей, итог: RVC работает offline, real-time используем DSP + лёгкую ML модель для pitch correction. Это входит в MVP.

**Dev1:** Согласен. Это реальная архитектура.

## 5. РАЗМЕР ДИСТРИБУТИВА И РАСПРОСТРАНЕНИЕ МОДЕЛЕЙ

**Dev2:** Ребята, у нас есть проблема с размером. Вот мои расчёты:
- HuBERT модель (acoustic features): 350MB
- RVC модели (base + fine-tuned): 200-300MB

2. **Lazy loading** — плагин качает модели при первом запуске
3. **Отдельная загрузка моделей** — пользователь скачивает базовые модели отдельно

**Designer:** А если пользователь не захочет скачивать 1GB?

**Dev1:** Есть ещё вариант — сжимаем модели. HuBERT можно квантизировать до 100-150MB без большой потери качества.

**Dev2:** Я могу это провести. Потеря качества будет ~3-5%, но это приемлемо.

**PM:** Окей, решение: 
- Сжимаем все модели (квантизация)
- Итого installler ~400-500MB
- При первом запуске предлагаем дополнительно загрузить расширенные модели (~200MB)
- Всё работает offline после загрузки

**Dev1:** Согласен.

## 8. GUIDE ТРЕК — ОБЯЗАТЕЛЬНОСТЬ И FALLBACK

**PM:** Следующий вопрос — guide трек. В нашей архитектуре есть предположение, что пользователь загружает guide трек (например, оригинальную песню или минус). Но что если он не захочет?

**Dev2:** Без guide трека система не может определить тональность и темп. Это критично для pitch correction и harmony generation.

**Designer:** Может быть, дать пользователю возможность вручную вводить тональность и темп?

2. Система пытается автоматически определить тональность (F0 detection)

**PM:** Это поддерживается нашими инструментами?

**Dev2:** F0 detection это стандартная задача. PYIN алгоритм работает хорошо для вокала. А manual input это просто UI с выбором тональности.

## 9. BACK VOCAL GENERATION — КАЧЕСТВО И АРХИТЕКТУРА

**Designer:** Теперь про back vocal generation. Это очень интересная фишка. Пользователь поёт мелодию, система генерирует гармонии. Вопрос: как мы это делаем?

**Dev2:** Есть несколько способов:
1. **Синтезированный drône** — используем синтезатор для создания гармоничных частей
2. **RVC-генерация** — используем RVC для клонирования голоса пользователя с другой высотой

**PM:** Какой лучше?

**Dev1:** Это сколько времени?

**Designer:** А гармонии, которые мы генерируем — они диатонические или хроматические?

**Dev2:** Для MVP я бы предложил диатонические гармонии. Это проще реализовать и звучит хорошо для большинства музыки.

**Designer:** И как мы выбираем, какие гармонии генерировать?

**Dev2:** Анализируем мелодию, определяем интервалы, предлагаем стандартные гармонические рисунки. Например:
- Третья выше
- Третья ниже
- Квинта выше
- И т.д.

**PM:** Это входит в MVP?

**Dev2:** Базовая версия да. 2-3 стандартных гармонических рисунка. В Phase 2 можем добавить кастомные.

**Dev1:** Я думаю это реально за 1.5-2 недели.

**PM:** Окей, back vocal generation в MVP. Базовые диатонические гармонии, RVC для синтеза.

## ИТОГОВЫЕ РЕШЕНИЯ

На основании обсуждения команда приняла следующие решения:

### MVP Feature Set
1. **ARA2** — откладываем на Phase 2
2. **VST3 плагин** для Windows и macOS (AU2 для macOS) — входит в MVP
3. **RVC voice synthesis** — offline режим, переписываем на Apache 2.0 для коммерческого использования
4. **DSP Pitch Correction** — real-time, лёгкая ML модель для detune (<5ms latency)
5. **Back Vocal Harmony Generation** — базовые диатонические гармонии, RVC синтез
6. **Voice Preset Creator** — RVC fine-tuning UI с progress tracking, background training
7. **Piano Roll** — отображение + простое редактирование нот, MIDI export
8. **Guide Track** — опциональный, fallback на ручной ввод тональности и темпа

### Технические Решения

**RVC Лицензия:**
- Переписываем RVC inference часть под Apache 2.0 лицензию
- Плагин распространяется под Apache 2.0
- Timeline: +2 недели, параллельно с интеграцией

**Latency Бюджет:**
- RVC inference offline (200-500ms, приемлемо)
- DSP pitch correction real-time (<5ms)
- Real-time preview через DSP, финальный результат через RVC offline

**Model Distribution:**
- Квантизация моделей (HuBERT, RVC) на 30-40%
- Итого installer: 400-500MB
- Lazy loading расширенных моделей при первом запуске
- Offline работа после загрузки всех моделей

**Back Vocal Generation:**
- Диатонические гармонии (не хроматические)
- Стандартные рисунки: +3rd, -3rd, +5th (примеры)
- RVC синтез для натурального звучания
- Offline генерация, ~300-400ms для 3-4 гармоний

**Guide Track:**
- Опциональный для определения тональности
- Fallback: PYIN F0 detection + manual input
- Tempo: предпосчитанный или ручной ввод (default 120 BPM)

**DAW Compatibility:**
- Windows: Ableton Live, FL Studio, Reaper (VST3)
- macOS: Logic Pro, Reaper (AU2 и VST3)

## ЗАКЛЮЧЕНИЕ

Команда пришла к консенсусу, что MVP с указанными решениями это реалистичный и амбициозный, но достижимый проект. Ключевые компромиссы:
- **ARA2 откладываем** (добавит 2 месяца)
- **RVC offline** (200-500ms приемлемо для use case)
- **Piano roll упрощённый** (но функциональный)
- **Voice Preset Creator в MVP** (это уникальная фишка продукта)

**Risks:**
- RVC переписывание может занять больше времени
- Integration тестирование может быть сложнее, чем ожидаем
- GPU требования для Voice Preset Creator на слабых машинах

**Mitigation:**
- Начинаем RVC переписывание сразу
- Создаём CI/CD для тестирования на разных DAW
- Даём CPU fallback для обучения (медленнее, но работает)

## Текущее состояние: AI Note Detection (22 мая 2026)

- Рабочий базовый режим: `librosa.pyin` + post-processing + pitch contour curve для каждой ноты.
- Pitch contour передается в UI компактной строкой `curve` и рисуется поверх note blocks как белая линия, чтобы видеть vibrato, drift in/out и slides.
- Экспериментальный ML/AI detector оставлен opt-in через `SO_USE_EXPERIMENTAL_NOTE_DETECTOR=1`; по умолчанию он не используется.
- Lyrics/ASR и syllable split временно выведены из дефолтного пайплайна: `SO_ENABLE_LYRICS=1` и `SO_ENABLE_SYLLABLE_SPLIT=1`.
- Причина: текущие word/syllable boundaries часто ошибаются и начинают портить хорошие note blocks, создавая ложные разрезы.
- Для следующего качественного шага нужен отдельный detector onset/syllable boundaries, обученный или хотя бы валидированный на вокальных фразах, а не чистый Whisper/text ASR.
